## Transient-error retry layer (`src/services/adapters/openaiCompatibleAdapter.ts`)

The openai-compatible adapter wraps the initial `client.responses.create`
call in `withRetryAround`, with exponential backoff and `Retry-After`
honoring (seconds form and HTTP-date form, plus `retry-after-ms`). Retry
runs INSIDE the adapter — not at the route — so every consumer of the
adapter (main chat, sub-agents, compaction distill/measure/summarize,
title generation, prompt-loop judge/critic) recovers from 429s and
other transient statuses automatically.

Key facts:

- Pre-stream only. Once any chunk has been yielded to the consumer, a
  retry cannot be transparent to the client (the route's
  `clear_assistant` only removes the last _committed_ assistant
  message, not the in-flight partial). The chat route's existing retry
  loop at `src/app/api/chat/route.ts:1093-1238` stays as the safety net
  for mid-stream failures.
- Defaults: `enabled=true`, `maxAttempts=3`, `baseDelayMs=1000`,
  `maxDelayMs=16000`, retryable statuses `{408, 409, 429, 500, 502, 503, 504}`.
  Configurable via the `retry: { ... }` block in `config.json` (same
  shape as `webSearch`). The adapter reads this through `loadConfig()`
  with a 60-second TTL cache; invalidate with
  `clearRetryConfigCache()` after tests.
- `isRetryableError` in `src/app/api/chat/sseStream.ts:74-99` was
  extended to duck-type any object with a numeric `.status`, so the
  chat route's fallback loop now correctly recognises `OpenAI.APIError`
  (it previously only matched axios errors and missed SDK-thrown 429s).
- The `logAdapter400` debug-dump helper now runs only after the final
  retry attempt, not per attempt, so a 429 storm no longer fills the
  repo root with `debug_400_*.json` files.

## Coding Guidelines

Apply appropriate design patterns and good programming practices to all code changes:

### Design Patterns

- **Prefer composition over inheritance** — use composition, delegation, and dependency injection to build flexible, testable components.
- **Apply SOLID principles** — single responsibility, open/closed, Liskov substitution, interface segregation, and dependency inversion.
- **Use established patterns where fit**:
  - Factory functions for complex object creation
  - Registry pattern for extensible feature sets (e.g., slash commands, tool handlers)
  - Adapter pattern for provider abstraction (see `services/adapters/`)
  - Facade pattern for simplified public APIs over complex subsystems
  - Strategy pattern for swappable algorithms (e.g., token counting, HTML extraction)
- **Avoid over-engineering** — use patterns when they genuinely simplify complexity, not to add abstraction layers for their own sake.

### Good Practices

- **Single Responsibility** — each function/module should do one thing well; keep functions small and focused.
- **DRY (Don't Repeat Yourself)** — extract shared logic into reusable helpers; avoid copy-paste code.
- **Explicit over implicit** — prefer clear, descriptive naming and explicit flows over clever shortcuts.
- **Type safety** — use TypeScript strictly; avoid `any` unless absolutely necessary; define proper types for all interfaces.
- **Error handling** — handle errors gracefully with meaningful messages; propagate errors up the call stack appropriately.
- **Modularity** — organize code into focused modules with clear public APIs; follow the existing `services/` and `tools/` directory structure.
- **Separation of concerns** — keep business logic separate from I/O, rendering, and orchestration.
- **Testability** — structure code so dependencies can be injected or mocked for testing.

### Refactoring Guidelines

- When modifying existing code, look for opportunities to improve structure.
- Extract new helpers into dedicated modules (e.g., `services/`, `tools/`) rather than bloating `index.ts`.
- Update this file when patterns or key architectural decisions change.

## Application overview

Locopilot is a terminal-based chat client for Ollama, providing a lightweight, local-first AI assistant with no cloud dependency. Key design goals:

- **Local & Private**: All inference runs through a local Ollama instance; no data leaves the machine.
- **Persistent State**: Host, port, and model selections are persisted in `config.json`. Conversations are automatically saved to a local SQLite database (`locopilot.db`).
- **Safety First**: Commands requested by the AI require explicit user approval by default.
- **YOLO Mode**: A high-trust mode that skips command confirmation for automated workflows, enabled via startup prompt, `--yolo`/`-y` flag, or `YOLO=true` environment variable.
- **Session Management**: Resume recent chats, switch between multiple active sessions (`/sessions`), or delete old ones (`/delete`).
- **Slash Commands**: Specialized commands for utility tasks:
  - `/model`: Refresh and switch LLM models mid-conversation.
  - `/settings`: Change App and Session settings (replaces initial startup prompts).
  - `/compact`: Force conversation summarization to recover context. Text after the command (`/compact keep the auth refactor details`) is a FOCUS note: it says what the summary should keep. It is normalised to ONE line (control characters to spaces, whitespace runs collapsed) before it reaches the prompt, so it can never emit a `Rules:` line, a fake `[USER]:` block label or a section header; it is capped at `COMPACT_FOCUS_MAX_CHARS` (2000) and an over-long note is REFUSED with a 400, never truncated. In the full prompt it lands between the section list and `Rules:` — the rules are read last and the note is explicitly subordinate to them — and it travels through every prompt of the map-reduce pipeline (chunks AND the combine step, which would otherwise dilute it away) and into the retry recursion. Automatic compactions pass none. The receipt line afterwards is rendered by `src/services/compact/receipt.ts` on both the manual and the automatic path (`⚡ Conversation compacted: 181,204 → 12,880 tokens (~93% smaller).`, `⚠️ Compaction could not reduce the context: …` when nothing was saved, `(<1% smaller)` when the saving rounds to zero, a quoted `Kept what you asked for: “…”` when a note was given, and a separate warning bubble when the result is still over the window).
  - `/dump`: Export the current conversation history, including the system prompt and tool call/tool result details, to a markdown debug file.
    - `/clear-images`: Remove all image attachments from the active conversation, both in client state and persisted SQLite, to free vision context and recover from 400 errors.
    - `/sessions`: Switch between multiple persistent chat histories.
    - `/delete`: Remove a session from the local database.
    - `/nudge`: Manually inject a tool-use reminder if the AI is hesitant.
    - `/help`: Application control and documentation.
- **Skills**: Self-contained `SKILL.md` packages with YAML frontmatter (`name`, `description`, optional `alwaysApply`, `autoInvoke`, `globPatterns`, `allowedTools`). Two discovery layers, project wins on name collision:
  - `project` (highest precedence): `<cwd>/.locopilot/skills/<name>/SKILL.md`
  - `user-profile` (lowest precedence): `~/.locopilot/skills/<name>/SKILL.md`
  - On Linux, `~/.locopilot` resolves to `$HOME/.locopilot`; on Windows, `os.homedir()` returns `%USERPROFILE%`, so the path is `%USERPROFILE%\.locopilot\skills\`. The `LOCOPILOT_HOME` env var, when set, overrides the user-profile root (useful for installs that relocate the user directory). The `create_skill` tool's optional `location` argument (`'project'` | `'user-profile'`, default `'project'`) lets the LLM write into either layer; the `Skill` object exposes its source as `skill.location`. See `src/services/skillManager.ts` for the loader and `src/tools/impl/createSkillTool.ts` for the tool schema.

## Tool-calling / Command-execution

Feature summary:

- **`run_command`**: Request shell commands. Uses a process registry for tracking and `Ctrl+X` for interruption.
- **`run_subagents`**: Run one or more isolated sub-agents sequentially. Each sub-agent gets a fresh ephemeral history, the normal tool set except `run_subagents` itself, and returns only its final answer back to the parent agent.
- **Process Registry**: Long-running commands are tracked by ID, allowing the AI to poll for output using a `check_process_output` tool if a command exceeds the initial 30s timeout.
- **Shell Precision**: On Windows, PowerShell is preferred. Commands are fed via `stdin` (e.g., `powershell -Command -`) to avoid quoting/tokenization issues across different shells. POSIX shell requests on Windows are automatically remapped to PowerShell with a warning.
- **Failure Analysis**: Non-zero exit codes trigger an AI-powered error summary ([errorSummary.ts](errorSummary.ts)) that distills technical `stderr` into a brief fix suggestion, which is then fed back into the history as a user-role nudge.
- **Sub-agent Terminal Output**: Web UI sub-agent output is attributed through structured `agentId` metadata rather than display-only text prefixes. Nested `run_command` requests still surface the normal approval prompt in standard mode, with the output routed to the requesting sub-agent's bubble.
- **Interruption**: `Ctrl+X` interrupts the tool-call loop or kills the running process without exiting the application. `Ctrl+C` remains a global exit signal.

## Markdown rendering

Feature summary:

- **`streamAIResponse`**: Provides real-time "typing" effect chunk-by-chunk. Intentionally skips markdown formatting during streaming for performance and accuracy.
- **`printAIResponse`**: Renders full markdown (tables, code blocks, formatting) using `marked` and `marked-terminal` once the stream is complete or for static messages.
- **Viewport Recovery**: Uses a viewport-aware strategy to replace raw streamed text with formatted markdown if the response fits on screen; otherwise, appends the formatted version after a separator.
- **Normalization**: Automatically fixes accidental global indentation in model responses to prevent formatting breakages (like misidentified code blocks).

## Session & Token Management

Feature summary:

- **SQLite Storage**: Uses `better-sqlite3` in WAL mode for reliable, concurrent message persistence.
- **Live Token Meter**: The status bar (src/components/StatusBar/StatusBar.tsx) shows real-time context usage (used / limit, estimated vs authoritative), the generation model, and a tokens-per-second badge. The t/s policy lives in two tested modules: src/services/tokenThroughput.ts (shared by the main chat loop and sub-agents) and src/app/lib/tpsDisplay.ts (display precedence/formatting), covered by scripts/test-token-throughput.mjs.
- **Tokens-per-second semantics**: The live rate rebaselines its clock at the first token-bearing chunk (model load and prompt processing are excluded), only updates while new tokens are actively arriving (it freezes instead of decaying while the model streams unobservable tokens such as tool-call arguments), and never reports a rate measured over less than one second of generation time - so bulk token arrivals (buffered provider flushes) can never spike the badge to six-figure t/s. Tool-call argument JSON is deliberately not counted into the live rate (it surfaces retroactively with no honest timestamp); the end-of-turn rate covers it. The end-of-turn rate aggregates every LLM call in the turn as sum(evalCount)/sum(evalDuration) - not last call wins - with a wall-clock fallback for providers that report no durations, tagged (est) in the UI. The prompt-processing rate is never displayed as generation speed. done events always carry the t/s fields (null when unknown) so stale previous-turn rates are cleared; error/abort paths clear the read-out scoped to the owning session, and a background stream's done lands in its own session slot as it arrives, so a switch-back never shows a frozen live estimate.- **Compaction speed (t/s)**: The t/s badge keeps updating while a conversation compaction runs - the distillation and summarisation/map-reduce LLM calls report live rates through the same shared meter (and sub-agent auto-compaction via reportTps), emitted as status events under the `compacting` phase. The `/compact` slash command consumes them in its own SSE loop and clears the badge when compaction ends. The token-measurement call is deliberately excluded (it generates at most one token, so it has no meaningful rate).

- **Switching conversations mid-turn** (`src/app/hooks/useChatStream.ts`, `src/app/lib/chatStore.ts`, `src/app/hooks/useDataLoaders.ts`, `src/app/lib/updateBatcher.ts`): every SSE frame is routed the moment it arrives, aimed at the session the server stamped on it; the reducer writes the top-level fields when that session is on screen and its `sessionStates` slot otherwise (`targetsBackgroundSession`; the placeholder `-1` counts as on screen while the new-chat view is). Nothing is replayed — the old buffer was replayed over a database reload that already held part of it (doubled text, lost text, swallowed errors, invisible running tool calls). Frames for a conversation that is NOT on screen are not dispatched one by one: `useChatStream`'s `dispatchOwned` sends them through `dispatchBackground`, a single global queue (`createBatchedDispatcher`, `updateBatcher.ts`) applied to the store together at most once per `BACKGROUND_UPDATE_INTERVAL_MS` (1 s, `constants.ts`; a FIXED window from the first queued update, not a debounce). Every dispatch re-renders what is on screen, so one dispatch per piece of text of a background stream used to block the main thread about half the time with a 253-message conversation open (3% after batching; measured on the dev build). The ordering rule lives in ONE place: `ChatProvider` hands out a `dispatch` that applies the queue FIRST, so a session switch (which restores a slot), the end-of-turn reload from the database (which older queued text would otherwise follow, duplicating it) and the steer-draft settle all see everything that arrived and no call site knows the queue exists. The reducer routes by the session on screen at APPLY time, so an update queued while its conversation was in the background and applied after it came on screen still lands correctly. Only `useChatStream` (and the provider) may use `dispatchBackground` — pinned by `scripts/test-update-batcher.mjs`, with the ordering replayed through the reducer in `scripts/test-chat-store.mjs`. A foreground `loadSessionMessages` for a session that is still streaming (`hasLiveTranscript`) switches the view and fetches nothing: the client's live copy is ahead of the database, which only has the steps the server has flushed. The turn's end reloads it from the database as before. A background approval waits in its slot (no modal over another conversation) and is restored on switch-back. `sendChatMessage` reads the session id, history and settings BEFORE the attachment upload `await`, so a message is always sent to and saved in the conversation it was typed in. Errors and Retry are per session (`retryPayloadsRef` keyed by session; failures are dispatched to the owning session). Only `session_created` promotes the new-chat mirror into a session (`SET_CURRENT_SESSION.adoptNewChat`); a new chat the user left before it was saved is moved into its real slot by `RENAME_STREAMING`. Covered by `scripts/test-chat-store.mjs` (a turn left at every frame and resumed must equal one never left). Navigation is ordered by a shared `LatestGate` (`src/app/lib/latestGate.ts`, created in `useDataLoaders` and passed to `useSessionActions`): opening a conversation (`loadSessionMessages`) and "+ New chat" (`handleNewSession`) each take a token when they start and re-check it when their fetch or server call returns, so the LAST click decides the view and a late load can never take it back. Background (end-of-turn) loads keep their own per-session tokens and are not navigation. Covered by `scripts/test-latest-gate.mjs`.

Not covered by memo: `SessionSidebar` and `StatusBar` still read the store and re-render on every update, and `useScrollManager` scrolls on every visible chunk.

An explicit `null` maximum is the server saying it knows none; an update that omits the field (`sseRouting` no longer turns an absent field into `null`) leaves `modelMaxNumCtx` alone. An answer for a model that is no longer selected is dropped (`isStaleNumCtxAnswer`). `describeContextWindow({ effective, modelMax })` is the whole display rule: no answer yet → "—" and no percentage; the window equals the maximum → "(model max: M)"; the server answered with no maximum → "(model max unknown)". The page never takes a minimum (a source pin fails if `Math.min` appears in these files) and there is no `DEFAULT_NUM_CTX` on the client (also pinned). `requestedNumCtx` is the GLOBAL setting as saved, kept for the Settings field and `/ctx` (which SAVES first and only then updates it, because the change makes the page ask the server again and that answer must read the new setting); it is `null` until `loadConfig` delivers it, is never shown as the window and is never sent. `/ctx` and the Settings field change only the global window: a provider with its own `numCtx` (NVIDIA, Airia, OpenRouter) keeps it. The page sends no `numCtx` in any body (chat, `/compact`, `/title`, `/dump`); Retry replays the stored body, which has none. Settings validates the field with `interpretNumCtxInput` (blank or malformed is an error, never a default; blank while the config is still loading means "unchanged"). - **Authoritative Stats**: Reconciles estimated local token counts (`tiktoken`) with authoritative metrics from Ollama (`prompt_eval_count`, `eval_count`) at the end of each turn.
- **Token Calculation**: Estimated counts [tokenizer.ts](tokenizer.ts) add 4 tokens per message plus role, content, and tool call overhead to match OpenAI-style counting as a robust local approximation.
- **Conversation Compaction**: The `/compact` command ([src/services/compact/](src/services/compact/)) uses a high-context LLM pass to summarize everything (decisions, code, paths) into a structured document — six sections (Goal, Changes, Decisions, Constraints, Open work, Key data) with file paths, commands and error messages reproduced exactly (a value the serialiser cut is reported as cut; the history usually carries a path and a size, never the changed symbols) — injecting a `[This conversation history has been compacted...]` preamble. A user-supplied focus note (`/compact <focus>`) is spliced in as a subordinate paragraph between the section list and the rules, on one line, through every prompt in the pipeline including the reduction's combine step and the retry. The summariser's instruction prompt is paid for out of the safe input budget before the history is fitted into what is left; at a small context window the pipeline falls back to the short prompt (the same six-section contract without the input-format explanation), and a window that is too small for either fails with a clear "this context window is too small to compact" error instead of sending an over-budget request.
- **Auto-Compact**: Compaction is triggered automatically at the start of each tool-call loop iteration (covers both between-tool-call growth and end-of-turn growth) once the history reaches the RESERVED-MARGIN trigger, `computeCompactionTriggerTokens(numCtx)` = the window minus a reply reserve of 25 % clamped to `[1500, max(13000, 8192·√(window/32768))]` (and capped at 40 % of the window), never later than 97 % of it — so the reserve grows with the window (8 192 at 32k, 23 170 at 262k, 46 340 at 1M) and every window at or below 82 532 behaves exactly as it did before the scaling — so 8192 fires at 6144 and leaves 2048 for the reply, instead of the old flat 92 % (7360, 640 left). A yellow `⚡ Context at N% — auto-compacting...` line is printed. If compaction fails or is a no-op, a warning is shown but the loop continues uninterrupted; two failures in a row in the same turn (`MAX_COMPACTION_FAILURES_PER_TURN`) stop the retries for that turn, because the trigger stays reached and a throw leaves the history unchanged. If the compacted result still exceeds 90 % of the context window (`COMPACT_ACCEPTANCE_HEADROOM`), compaction first DROPS the oldest messages of the preserved recent window (`planWindowTrim` in `src/services/compact/windowTrim.ts`, charged against what the summary message — preamble, summary and a worst-case notice — leaves of that budget) and appends a `[Note: N earlier messages were dropped to fit the context window…]` line to the summary so the model knows the window it can see is incomplete; only if that is still not enough (or nothing is droppable, e.g. the last row is a tool result whose assistant cannot be left behind) does it retry up to twice more with a stronger aggressiveness factor that shrinks preservation budgets and summary targets. Trimming is preferred because the retry re-summarises an ALREADY-COMPACTED array — a summary of a summary, the worst quality leak in the pipeline — while dropping the oldest recent turns costs context but not fidelity, needs no model call, and still helps when the retry budget is exhausted. The most recent user prompt is always preserved verbatim across all passes: the trimmer never cuts it, and hoists it to the front of the window when the cut would pass it. Large tool outputs are distilled in the PRESERVED WINDOW FIRST and then in the older slice with what is left of a per-window call cap (`computeDistillCallCap`: one call per 16k of window, clamped to `[2, 8]`, spent on the LARGEST results — never newest-first), so a history with dozens of huge outputs can no longer turn one compaction into dozens of sequential model calls. If the result is still over the model context limit after all passes, a red warning is printed so the user can intervene.
- **Compaction awareness (LLM-visible)**: The post-compaction nudges are LLM-visible and self-reporting. The main chat loop keeps a per-request `compactionsSinceLastPrompt` counter (resets naturally per turn — each user message is a new request) and each auto-compaction nudge tells the model how many times the history has been compacted since its last message plus the current context-usage percentage; from the second compaction onward it adds a directive to economise on tool output and reconsider the approach. Sub-agents track and report their own local count the same way; the parent's count is deliberately not inherited. Synthetic server-generated user-role nudges (post-compaction notice, empty-response recovery, prompt-loop continuation) are prefixed with `SYNTHETIC_NUDGE_MARKER` (`src/services/compact/constants.ts`) and suffixed with `[End system notice]`; `isSyntheticNudge` in `src/services/compact/split.ts` excludes them from the latest-user-message verbatim anchor, so the real user prompt is never summarised away by a second in-turn compaction. Anchor behaviour is covered by `scripts/test-compact-anchor.mjs` (`npx tsx scripts/test-compact-anchor.mjs`).

### How conversation compaction works (the mental model)

**The problem.** Every turn re-sends the whole transcript to the model, and the bulkiest part of a transcript is not the conversation — it is the tool output (a file dump, a test run, a build log). At some point the transcript plus the reply no longer fits the model's context window and the turn has to be made smaller. Compaction is that: the older part of the transcript is replaced by a summary the model wrote, the recent part is kept as it is, and the turn carries on.

`compactHistory` (`src/services/compact/orchestrate.ts:131`) is the whole flow. The chat route calls it at the top of each tool-call loop iteration (`src/app/api/chat/route.ts:1517`); the sub-agent loop runs the same trigger against its own window (`src/tools/impl/subAgentTool.ts:446`) and also force-compacts after a provider context-limit 400 (`src/tools/impl/subAgentTool.ts:1193`).

**1. The trigger — a reserved margin, not a percentage.** `computeCompactionTriggerTokens(numCtx)` (`src/services/compact/budget.ts:157`) fires at `min(numCtx − reserve, floor(0.97 × numCtx))`. The reserve is the REPLY budget — the room the model needs to finish its answer once compaction has fired — and `computeCompactionReserveTokens` (`budget.ts:124`) sizes it as `clamp(floor(0.25 × numCtx), 1500, max(13000, floor(8192 × (numCtx / 32768) ^ 0.5)))`, finally capped at 40 % of the window. It grows with the square root of the window, not with the window, because a bigger window makes the QUESTION bigger, not the answer: 8192 → reserve 2048, fires at 6144; 32768 → 8192, fires at 24576; 262144 → 23 170, fires at 238 974; 1 048 576 → 46 340, fires at 1 002 236. Every window at or below ~82 500 tokens is unchanged by that curve. The route compares the provider's own prompt count when it has one and the calibrated local estimate plus the tool schemas otherwise (`src/app/api/chat/route.ts:1493-1501`), and two failures in a row in the same turn stop the retries for that turn (`MAX_COMPACTION_FAILURES_PER_TURN = 2`, `src/constants.ts:90`).

**2. The split — two slices, one anchor.** `splitHistoryForCompaction` (`src/services/compact/split.ts:141`) divides the history into an older slice that will be summarised and a recent window that is kept verbatim. The window's budget is `clamp(floor(0.12 × numCtx), max(300, floor(0.03 × numCtx)), floor(0.3 × numCtx))` at aggressiveness factor 1 (`split.ts:155-161`; `constants.ts:126-129`), with a floor of 2–8 messages by window size (`split.ts:31`); the normal split keeps at least 25 % of the messages for the summariser (`MIN_TO_SUMMARISE_RATIO`, `constants.ts:130`), and the cut never bisects an assistant + tool block (`split.ts:58`). The ANCHOR is the latest REAL user message: it is hoisted into the window and never summarised. Server-generated nudges (post-compaction notice, empty-response recovery) carry `SYNTHETIC_NUDGE_MARKER` and are skipped by `isSyntheticNudge` (`split.ts:40`), so a second compaction inside the same turn cannot summarise away the real prompt. Below `MIN_SUMMARISE_TOKENS` (200) the compaction refuses to run.

**3. The distillation — one call per oversized tool output, two brakes.** `distillToolMessages` (`src/services/compact/distill.ts:532`) sends one oversized tool output per model call and replaces it with a short digest. TWO brakes bound the work: a CALL cap on the number of round-trips (`computeDistillCallCap`, `budget.ts:210` — one call per 16k of window, clamped to `[2, 8]`) and a PREFILL budget on how much text the calls may read (`computeDistillPrefillBudgetTokens`, `budget.ts:371` — one window's worth for the whole compaction). The budget is spent LARGEST FIRST (`planDistillation`, `distill.ts:465`; never newest-first, because the newest results are what the model is actively reasoning about). A candidate is a `tool` row of at least 1200 characters whose owning assistant row is in the same slice; a row whose assistant is in the other slice is an orphan and is never touched. A failed call (400, timeout, dropped stream) leaves that output VERBATIM and the pass continues — only an abort propagates (`distill.ts:686-690`). The preserved window is distilled FIRST (`orchestrate.ts:319`) because the window is kept verbatim in the result, so digesting it shrinks the RESULT; the older slice gets what is left of the call cap (`orchestrate.ts:341`).

**4. The adaptive spend — the leftover prefill budget.** When the result is still over budget after the trim, the prefill budget the first passes did not spend buys extra digests of the PRESERVED WINDOW (`orchestrate.ts:613-760`). It digests the window and not the older slice, because the window is kept verbatim: digesting it shrinks the result with NO extra summariser call, whereas digesting the older slice would only shrink the summary's INPUT and would need another whole summarisation pass. The extra calls are charged against the SAME budget (so one compaction's prefill never exceeds one window) and capped at 32 (`TOOL_DISTILL_EXTRA_CALLS_MAX`, `constants.ts:488`) — a latency guard, not a budget. The spend skips rows that are already digests (a digest can be longer than the output it replaced) and rows whose call already failed (a failure is not retried), and the new digests are kept only when they made the result SMALLER (`orchestrate.ts:707-711`).

**5. The summariser — one pass, or map-reduce.** `produceConversationSummary` (`src/services/compact/reduce.ts:215`) issues one request when the serialised history fits, and otherwise splits it into chunks (`splitHistoryIntoChunks`, `split.ts:300`), summarises each chunk on its own, and combines the partials in batches of 4 (`REDUCTION_FAN_IN`, `constants.ts:639`) for at most 8 rounds (`MAX_REDUCTION_ROUNDS`, `constants.ts:652`), after which the remaining parts are concatenated without another model call (`reduce.ts:595`). The instruction prompt is paid for out of the safe input budget (60 % of the window, `constants.ts:637`) BEFORE the history is fitted into what is left; when the full prompt leaves less than 512 tokens of history allowance the pipeline switches to the short prompt (the same six-section contract without the input-format explanation), and when even that leaves too little it fails with "this context window is too small to compact" instead of sending an over-budget request (`reduce.ts:138-210`, `reduce.ts:288-292`). The summary is a STRUCTURED DOCUMENT with six named sections — Goal, Changes, Decisions, Constraints, Open work, Key data (`SUMMARY_SECTIONS`, `constants.ts:27`) — rendered from that one list, so the prompt cannot drift from the constant. The `/compact <note>` focus note is a subordinate line: normalised to ONE line (`normaliseCompactionFocus`, `focus.ts:107`), capped at 2000 characters, and placed between the section list and `Rules:`, so the rules are read last. It travels through the chunk prompts, the combine prompt and the retry recursion.

**6. The verdict and the trim.** `evaluateCompactionSizes` (`budget.ts:184`) returns three verdicts: `aborted` when the result is not smaller than the history it replaced (that throws — "failed to reduce history size"); `retry` when the result is above `floor(0.9 × numCtx)` (`COMPACT_ACCEPTANCE_HEADROOM`, `constants.ts:187`); and `confirm` when the estimate lands within 5 % of that boundary (`COMPACT_MEASURE_CONFIRM_BAND_RATIO`, `constants.ts:199`), and only then is ONE live measurement paid for to settle the tie (`measure.ts:22`). The estimate stays the number the UI shows. The trim (`planWindowTrim`, `windowTrim.ts:174`) drops the OLDEST preserved messages until the window fits what the summary header, the worst-case trim notice and the SYSTEM PROMPT leave of the acceptance budget (`computePreservedWindowBudget`, `windowTrim.ts:105`), and appends `[Note: N earlier messages were dropped to fit the context window…]` to the summary so the model knows the window it can see is incomplete. It never drops the last message, never leaves an orphan tool result at the head, and hoists the anchor to the front rather than cutting it. Trimming is preferred to re-summarising because the retry re-summarises an ALREADY-COMPACTED array — a summary of a summary, the worst quality leak in the pipeline — while dropping the oldest recent turns costs context but not fidelity, costs no model call, and still helps when the retry budget is spent. The retry (at most twice, with a stronger aggressiveness factor) is the last resort (`orchestrate.ts:760-800`).

**7. The re-attached files stub.** `buildRecentFilesMessage` (`recentFiles.ts:773`) re-states the five most recently touched files (`RECENT_FILES_MAX_FILES = 5`): the path always, the file's content only when the WHOLE file fits the per-file budget (1000 tokens) — a file that does not fit is named by path, line count and a hint, because a truncated head is not a smaller version of the same information. The budget is `min(5000 tokens, 10 % of the window)` and whatever room is left below the acceptance boundary (`computeBudgetForResult`, `recentFiles.ts:620`); below 300 tokens there is no stub at all. The stub is built AFTER the final verdict (`orchestrate.ts:801`), so it can neither trigger a retry nor be lost to one, and `attachRecentFilesMessage` (`recentFiles.ts:671`) refuses the attach outright if it would un-shrink the history or push the result past the acceptance boundary. It is an assistant message (never a user row: a user row would become the next compaction's anchor) placed between the summary and the window.

**8. The receipt.** `formatCompactionReceipt` (`receipt.ts:123`) is the one place the user is told what happened: `⚡ Conversation compacted: 181,204 → 12,880 tokens (~93% smaller).` — the before/after counts and the percentage saved, rounded and prefixed with `~` because both counts are local estimates (`(<1% smaller)` when the saving rounds to zero); `⚠️ Compaction could not reduce the context: …` when nothing was saved; the quoted focus note when one was given; and a separate warning bubble when the result is still over the window. The same formatter renders the manual `/compact` receipt (`src/app/hooks/useSlashCommands.ts:541`) and the automatic one (`src/app/lib/sseRouting.ts:383`).

**9. The token estimate.** Every count above is a local tiktoken estimate (`src/services/tokenizer.ts`): 4 tokens per message plus role, content and tool-call overhead, plus 2 for the array; `encoding_for_model` throws for a model tiktoken does not know and the tokenizer falls back to `cl100k_base`. The CALIBRATION (`src/services/tokenCalibration.ts`) learns the ratio between that estimate and the provider's own prompt count, per (provider, model, request class) — the classes are `chat`, `summarise` and `distill` — and multiplies every budgeted count by it. The rule that makes it safe: the calibration may only ever make Locopilot think it has LESS room than it has. A sample whose ratio is below 1 is rejected outright and the factor is clamped to `[1, 3]` (`tokenCalibration.ts:231-232`); over-counting is the safe direction. The compaction PINS the factor for the whole pass (`orchestrate.ts:131`), so the before and after counts are measured on the same scale.

**The constants that matter**

| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

**Why it is shaped this way.** The trim comes before the retry because a summary of a summary is the worst quality leak in the pipeline: the second pass has no dialogue left to read, only the first pass's paraphrase, and everything it compresses again is one paraphrase further from the facts — while dropping the oldest recent turns costs context but not fidelity and needs no model call. The focus note cannot override the rules because it is a prompt instruction, not a filter: it may raise the salience of what the user names, but four explicit prohibitions stop it from licensing an omission or an invention, and it is read before the rules, not after. The calibration is one-directional because a factor below 1 would mean the provider counted the request as CHEAPER than the tokenizer did, which is the one direction that turns a mis-estimate into an overflow, a 400 or a lost compaction; over-counting only makes Locopilot compact early. The stub is attached after the verdict because it must not be able to cause a retry, and because the retry recursion must never read a few thousand tokens of file heads as prose to compress. The summary is not capped below the window because it is the model's ONLY memory of the compacted turns: a cap that silently truncated it would lose exactly the facts it exists to preserve, so the window itself is the only hard ceiling.

**Known limitations.**

- The distillation caps are per COMPACTION, not per turn: a turn that compacts three times gets three call caps and three prefill budgets (`orchestrate.ts:312-318`).
- The recent-files stub is capped at 5 files and 5000 tokens (`constants.ts:516`, `constants.ts:532`) — 0.5 % of a 1M-token window — so at a large window it is nearly pointless; it earns its place at 8k–32k.
- The manual `/compact` route confines the stub's reader to the HOME directory: it calls `getAgentWorkingDirectory()` with no scope (`src/app/api/compact/route.ts:347`), whose default is `process.env.USERPROFILE || os.homedir() || process.cwd()` (`src/tools/workingDirectory.ts:24-33`). The chat route confines it to the request's working directory instead.
- The summariser's output allowance is `min(numCtx, max(floor(target × 1.2), min))` (`src/services/compact/summarize.ts:782-787`), so a large window asks for a very large summary: at 1M tokens the target is ~104 857 tokens and the allowance ~125 829.
- The preserved window can exceed its own budget by up to one message: the budget is checked BEFORE the next message is added (`split.ts:188-199`), and the anchor-rescue path adds the anchor and the post-anchor turns on top of the budgeted window.
- Images and the sub-agent loop are not calibrated: a request carrying images is never sampled (`src/app/api/chat/route.ts:2031-2038`, `tokenCalibration.ts:327`) and images are charged a flat 1024 tokens each (`src/constants.ts:22`); the sub-agent loop records no sample of its own, so it uses the factor the main loop learned.
- The compaction model may differ from the main model (`src/app/api/chat/route.ts:421`), so the compaction may run on a different provider with a different window; the receipt's overflow warning deliberately uses the MAIN window, because that is the window the next turn runs in.

## Empty-response recovery (`src/services/emptyResponseRecovery.ts`)

Feature summary:

- **Shared policy**: Detection of "empty" assistant replies (`hasMeaningfulAssistantContent` — empty/whitespace, or a bare reasoning-channel label like `thought`/`analysis`/`final`/`commentary` after special-token stripping), the attempt cap (`MAX_EMPTY_RESPONSE_RECOVERY_ATTEMPTS`, 3), the synthetic user-role nudge (`buildEmptyResponseRecoveryNudge`, marker-prefixed so compaction never anchors on it), and the streak tracker (`EmptyResponseRecoveryTracker`) live in one module used by both the main chat loop (`src/app/api/chat/route.ts`) and the sub-agent loop (`src/tools/impl/subAgentTool.ts`), so the behaviour can never drift between the two surfaces.
- **Loop contract**: On an empty reply, the loop pushes the empty assistant message plus the nudge into the LLM context (LLM-context only — nudges are deliberately NOT persisted to SQLite) and re-enters the loop, up to the cap. A tool-call turn or a meaningful reply resets the streak. After the cap is exhausted the empty reply is accepted as final (sub-agents surface `[Sub-agent completed without a final text response.]` to the orchestrator). Sub-agents emit an `empty_response_recovery` diagnostic and write a `[empty response #N/3]` line into their log bubble while retrying.
- Covered by `scripts/test-empty-response-recovery.mjs` (`npx tsx scripts/test-empty-response-recovery.mjs`).

Feature summary:

## MCP OAuth client registration & diagnostics

MCP servers that need OAuth 2.1 carry an `oauth` block in `~/.locopilot/mcp.json`.
Client identity is chosen by a priority chain (`resolveClientRegistrationStrategy`
in `src/mcp/oauthDiagnostics.ts`):

- `configured` — a pre-registered `oauth.clientId` (plus `oauth.clientSecret`
  when the server requires one) always wins.
- `cimd` — SEP-991 Client ID Metadata Documents, only for authorization
  servers that genuinely require them (NOT Atlassian). Set
  `oauth.clientMetadataUrl` to a **public HTTPS URL with a non-root
  pathname**; the authorization server fetches that document to identify
  Locopilot. `configLoader` validates the shape eagerly.
- `dcr` — RFC 7591 Dynamic Client Registration, the SDK's fallback. Locopilot
  ALWAYS sends `client_name` via `buildOAuthClientName(serverName)`, because
  some servers (Atlassian) reject DCR with HTTP 400 when it is absent. This is
  how the `atlassian` server actually authenticates: plain DCR, the same
  mechanism Claude Code uses, despite Atlassian also advertising
  `client_id_metadata_document_supported: true`.
- `unavailable` — neither CIMD nor DCR; the user must supply `oauth.clientId`.

`classifyMCPOAuthFailure` (same module) labels a failed connect as a
discriminated-union failure and decides the handle status. A genuine 401 keeps
the live transport alive for the later token exchange; every other auth
problem — including a rejected or unsupported client registration — surfaces as
`auth_required` with an accurate message and reaps the transport. Only
`interactive` connects (the Authenticate button / `/mcp auth`) can reach the
registration branches, so background/eager connects never report an auth
problem the user cannot act on. The classifier also guards on the stashed
authorization URL: an AS that advertises CIMD would otherwise have _every_
post-consent failure mislabelled as a registration problem, but a stashed URL
proves the SDK already had a client identity, so registration cannot be the
cause. The real authorization URL is stashed in memory
(`peekAuthorizationUrl` / `clearAuthorizationUrl` in `oauthProvider.ts`) and
rendered by the sidebar; no placeholder URL is ever fabricated.

MCP/OAuth diagnostics land in `logs/locopilot-debug.log` via
`debugLog.diagnostic({ layer: 'mcp', phase: 'oauth_*', failureKind, … })`
(`src/app/lib/debugLogger.ts`). Use the `oauth_discovery`, `oauth_redirect`,
`oauth_callback`, `oauth_token_exchange`, or `oauth_error` phases when extending
the flow. Regression coverage lives in `scripts/test-mcp-oauth.mjs`
(`npm run test:mcp-oauth`).

- **Adapter mapping convention**:
  - Canonical request concepts belong on `ChatParams` / `StreamChatParams` as typed fields (e.g. `maxOutputTokens`), not buried inside `options`.
  - Each adapter is responsible for translating canonical fields into provider-native request fields:
    - Ollama: `maxOutputTokens` → `options.num_predict`
    - OpenAI-compatible: `maxOutputTokens` → `max_output_tokens` on the Responses API (`client.responses.create`, `/v1/responses`). The Chat Completions field `max_completion_tokens` is not sent by this adapter.
  - Keep provider-specific parameter names out of callers. Legacy `options.*` passthrough may remain as a fallback, but new code should prefer the canonical field.
  - Document the mapping in both JSDoc on `ChatParams` and in `OPENAI_COMPATIBILITY_MIGRATION.md`.
  - When adding a new provider, implement the same canonical fields so callers stay provider-agnostic.

- **numCtx cap resolution** (`src/services/capResolver.ts`, `src/services/contextWindow/resolveNumCtx.ts`, `src/services/llmContextLimit.ts`, `src/app/api/numctx/route.ts`):
  - The SERVER decides the window: `effective = min(setting, modelMax)` when the model's maximum is known, and `effective = setting` when it is not (the page then says "model max unknown"). The setting is the active provider's own `numCtx`, otherwise the global `config.numCtx`. There is no Settings control for a provider's window; edit `config.json`. A request body's `numCtx` is NEVER read, by the chat, compact, title or dump route (pinned in `scripts/test-numctx-resolver.mjs`). `resolveNumCtx` returns `{ requested, modelMax, effective, known, source, probeError }`; the same object is the body of `GET /api/numctx?providerId=&model=` (both optional, defaulting to the saved selection; it takes an id and a model name, never a URL). Every chat `status` event carries `tokenLimit` (effective) and `modelContextLimit` (the maximum, `null` when unknown).
  - The Ollama adapter sends the effective window as `options.num_ctx`; the OpenAI-compatible adapter never sends it. Ollama Cloud ignores `options.num_ctx`. Probed with `beam` (2026-11-11): a 2,846-token prompt reported the same `prompt_eval_count` with `num_ctx` 256 as with none, and `num_ctx` 4,000,000 was accepted without error. The provider's own prompt limit is what applies, so the clamp to the model's maximum still matters for cloud models. The owner reports that local runners DO honour `num_ctx` on their own hardware (checked here only against `qwen3:0.6b`: it truncates to the window and clamps to the model's `context_length`); for those, the runner reload described above applies. Still unexplained: the sub-agent's HTTP 400 "context window exceeds limit" — `num_ctx` cannot be its cause.
  - Where the maximum comes from: Ollama (local or cloud) `/api/show` (`model_info.<arch>.context_length`, or the Modelfile's `PARAMETER num_ctx N` for RoPE-scaled models, which `getModelContextLimitFromInfo` scans FIRST); llama.cpp `meta.n_ctx` of a LOADED model only (never its `context_length`, which is the trained window; an unloaded model is unknown; detected from `details.parent_model === 'llamacpp'` because the adapter moves `owned_by` there); other OpenAI-compatible servers the `/v1/models` entry; NVIDIA publishes none, so it is unknown; any provider's 400 that states a limit (`maximum context length is N tokens`, or `exceeds the available context size (N tokens)`) is learned. `/api/ps` is NOT a source (it reports a runner's current allocation and can under-cap).
  - Probe and cache rules (`capResolver.ts`; keyed on (baseUrl, provider kind, model) exactly as supplied): a probe is abandoned after 10 s (a race against a timer; `fetchModelInfo` takes no abort signal); a success is cached 5 minutes, including "answered, no maximum"; a failure or timeout is cached 60 s, so a dead provider does not stall every turn; a limit learned from a 400 is cached 5 minutes and is never replaced by a probe while fresh; concurrent callers share one probe. Invalidate with `invalidateCapCache(baseUrl?, model?)` on a model, endpoint or provider change. A change of the SETTING is not a reason: the maximum does not depend on it, and `PUT /api/config` no longer clears the cache for it. A failed probe is logged as the `numctx_probe_failed` diagnostic.
  - The compaction window is resolved against the COMPACTION model's own maximum (it can be lower than the main model's), with the compaction provider's own `numCtx` when one is chosen. The main and compaction windows are resolved in parallel, at turn start and at a model switch; for the same endpoint and model the probe is shared. `/title` uses the same resolver, with its own smaller cap applied in `generateSessionTitle`; `/dump` only labels the window.
  - Retry and mid-turn model switches use the setting AS IT IS AT THE MOMENT OF USE. Retry replays the stored body, which carries no window; the server resolves it when the retry arrives. A mid-turn switch re-reads the saved config (`resolveNumCtxForModel(true)`, `settingSource`), including the provider's own window, so a setting lowered mid-turn takes effect at the next switch. The turn start uses the config it loaded.
  - The 400-driven discovery path (`adoptDiscoveredContextLimit`, in the chat route and in sub-agents) records the limit in the cache and the SSE `status` event. Nothing writes the window to the database. Older databases still carry a `sessions.num_ctx` column (all NULL in the live database); nothing in `src` reads or writes it, and `history.ts` creates only the `last_*` token columns.
  - Config read failures (`readConfig`, `src/services/configManager.ts`): a MISSING `config.json` is created with defaults (`buildFreshConfig`: window 131072, no provider, no model), and the window default is written only at that moment. A file that EXISTS but cannot be read or parsed is never overwritten: every route that reads the config answers 503 with the reason (`config.json exists but could not be read ...`), and the page shows it on screen (`useDataLoaders.loadConfig` dispatches it as the error). The Ollama path logs the body of any 400 as an adapter `error` diagnostic (`logOllamaBadRequest`, `src/services/adapters/ollamaAdapter.ts`).
  - Refusals before a model is called (`src/services/contextWindow/configProblem.ts`): chat, compact, title and dump answer 409 with the reason when no provider matches the request ("No model is set up yet ... choose a model") or when no context size is set for the provider or the global setting ("No context size is set ..."). The same check covers an explicit compaction provider. No server code assumes a window: `DEFAULT_NUM_CTX` is removed, and a missing window is an error (`requireWindow`), except inside the sub-agent and compaction guards, where 0 already means "no window". The Ollama adapter omits `num_ctx` when the window is 0.
  - Adding a provider (`ProviderSection.tsx` at the top of Settings, `POST /api/providers`, `src/services/providerValidation.ts`): the form takes a name, a kind (Ollama or OpenAI-compatible), a server address, an optional API key and an optional model. The server appends ONE validated entry to `config.json` (it does not wait for the Save button), makes the id from the name and never reuses one, stores the address without a trailing slash (and without a trailing `/v1` for an OpenAI-compatible server, because the adapter appends it), refuses a duplicate name, and never returns the key (`hasApiKey` only). The page then fetches the model list again (`fetchModelList`, shared with the page's own loader) and says whether the provider answered. Add only: editing or removing a provider and a provider's own `numCtx` are still done in `config.json`. `PUT /api/config` and the endpoint validate providers with the same function.
  - A context-limit 400 that names NO number (`isNumberlessContextLimitError`, `classifyContextLimitError` in `src/services/llmContextLimit.ts`) gets one forced compaction and one re-send of the turn, in the main loop (`providerLimitRetriedThisTurn`, `compactionForcedByProvider`, `continue outer`) and in sub-agents. It teaches no cap. Only one phrasing is confirmed (`invalid params, context window exceeds limit`, Ollama Cloud, C-005); the list is widened only from a logged occurrence. NEEDS CLARIFICATION is marked at each use.

- **Mid-turn model switching** (`src/app/lib/modelSwitchRegistry.ts`, `src/app/api/chat/switch-model/route.ts`, `src/app/api/chat/route.ts`, `src/tools/impl/subAgentTool.ts`):
  - SSE is server→client only, so a streaming turn has no inbound channel. `POST /api/chat/switch-model` is the side channel — same pattern as `/api/approve`. It writes a pending `{ model?, providerId?, compactionModel?, compactionProviderId? }` into a per-session in-memory registry; a session with no streaming turn gets a 404, which the client treats as "the config update already covers the next turn".
  - **Boundary semantics, not interruption.** The switch is consumed at the top of the main `outer:` tool-call loop and at the top of each sub-agent iteration. An in-flight LLM call is never aborted, so the latency of a switch is bounded by the longest single tool call in progress.
  - **The sub-agent hook is load-bearing.** A `run_subagents` batch parks the main loop for its whole duration, so a top-of-loop check alone would delay the swap until the batch returned. `SubAgentConfig.refreshModels` (wired to `applyPendingModelSwitch` in `buildRequestContext`, called at the top of `runSingleAgent`'s `while`) is what makes the swap land mid-batch. It mirrors the existing `approvalRequester` closure — a callback on the config object that reaches back into route scope. When editing either loop, keep both consumption points.
  - **In-place mutation is deliberate.** `requestContext.subAgent` is mutated, never rebuilt: `subAgentTool` captures that object once by reference and reads `config.model` fresh each iteration, so mutation is what propagates. Rebuilding the context would strand already-running sub-agents on the old model. Provider fields are `delete`d when the new model has no configured provider, so a stale `apiKey` can't survive a swap.
  - `model` in the chat route is a `let`, and the model-dependent setup — `resolveNumCtxForModel`, `resolveVisionForModel`, `resolveSamplingSupportForModel`, `resolveCompactionRuntime` — is factored into closures reused by both initial setup and the switch, so a swapped model never runs on the previous model's verdicts.
  - Main and compaction models switch independently. Because `resolveCompactionModel('', model)` returns the main model, a "Same as main" user's compaction model follows a main-model switch for free.
  - The server confirms with a `status` event of phase `model_switched` carrying the resolved `model` and `compactionModel`. The client adds the session to `modelSwitchPendingSessions` on request (`SET_MODEL_SWITCH_PENDING`, per session, so a switch asked for in one conversation never shows as pending in another) and clears it on that event, scoped to the frame's owning session — the status bar shows "(switching…)" rather than flipping optimistically on click.
  - The `/model` slash command needs no equivalent: `InputArea` unmounts `ChatInput` while streaming, so slash commands are unreachable mid-turn by construction.

- **Mid-turn steering messages** (`src/app/lib/steerRegistry.ts`, `src/app/api/chat/steer/route.ts`, `src/components/SteerInput/`, `src/app/api/chat/route.ts`, `src/tools/impl/subAgentTool.ts`):
  - Same side-channel/boundary-consumption shape as mid-turn model switching above, with two differences: the registry is a per-session FIFO **queue** (`SteerMessage[]`, not a merge-on-write object — several messages can be typed before either loop reaches its next boundary and none may be dropped), and entries carry a `target: 'main' | 'subagent'` so a drain can be scoped to whichever loop is asking. `modelSwitchRegistry.ts` exports `hasActiveTurn` so the new registry shares turn-liveness tracking instead of duplicating it.
  - `target: 'main'` entries are drained in the chat route's `outer:` loop right after `applyPendingModelSwitch()` and **before** auto-compaction — pushed as an ordinary, unmarked `user` message (not a `SYNTHETIC_NUDGE_MARKER` nudge) into both `currentMessages` and `pendingAppends`, so it is persisted normally and becomes the newest real user message. This is deliberate: compaction's existing "preserve the latest user message verbatim" anchor (`isSyntheticNudge` / `src/services/compact/split.ts`) protects it automatically, with no special-casing.
  - `target: 'subagent'` entries are drained by a new `SubAgentConfig.applySteerMessages?: (messages, agentId) => Promise<void>` hook, called in `runSingleAgent`'s loop right after `config.refreshModels?.()`. Unlike `refreshModels`, it cannot mutate shared config in place — a sub-agent's message history is a `while`-loop-local variable, not part of the shared `SubAgentConfig` object — so `runSingleAgent` passes its own `messages` array in explicitly. The hook only drains entries pinned to the currently-running `agent.id`; it never touches `target: 'main'` entries, so a main-targeted steer can never land mid-batch ahead of that sub-agent's own tool-call/tool-result rows.
  - **No new "is a sub-agent running" registry.** `run_subagents` already executes agents sequentially (never in parallel), so at most one `agentId` is ever active. The client derives this purely from SSE events it already receives (`tool_call` for `run_subagents` starting, `subagent_output`/`subagent_chunk` carrying the active `agentId`, the matching `tool_result` clearing it) into a PER-SESSION `activeSubagentId` (`SET_ACTIVE_SUBAGENT`, routed to the owning session like every per-session field; `ChatState.activeSubagentId` mirrors the visible session's, and `STOP_STREAMING` clears only the stopped session's) — see `src/app/lib/sseRouting.ts`. One conversation's running sub-agent is never offered as another conversation's steer target.
  - **Client hold-until-ack invariant (per conversation).** `InputArea` mounts a slim, always-available `SteerInput` next to Stop while streaming (instead of hiding the composer), with a main/sub-agent toggle shown only when `activeSubagentId` is set (defaults to sub-agent). Sending stores the draft in `chatStore.steerDrafts` keyed by the session it was sent FOR (not whichever conversation is on screen when the answer arrives), so one conversation's pending steer never locks another's steer box, and does **not** clear/echo it until a matching `status` event with `phase: 'steer_applied'` (carrying `steerId`) arrives for that session — that event alone adds the message to the transcript. Any path that ends without that ack — the `POST /api/chat/steer` 404s, the turn aborts, or the turn completes — routes through the `STOP_STREAMING` reducer case for THAT session (`settleSteerDraft`), which compares the transcript just reloaded from the database against the draft: the draft records `copiesAtSend`, the number of user messages already carrying that exact text when it was sent, and ONE MORE copy means the server saved the steer itself (it does when the turn ends before a tool step could pick it up, and the ack can also race the draft), so nothing is restored — restoring it as well made the user send it twice. Otherwise the text goes into `chatStore.steerRestoreTexts` under that session; `ChatInput` puts a session's entry in THAT session's composer (on mount, and when the user opens the session while the composer is already mounted) and clears it with `CLEAR_STEER_RESTORE` — it can never land in another conversation's composer. Kept separate from `inputDraft`, which has its own history-navigation lifecycle.
  - **Server-side salvage is a backstop, not the guarantee.** `salvageSteerMessages()` runs just before the final and the abort-path `flushSessionState()` calls, folding any still-queued entries (e.g. pinned to a sub-agent that never got another iteration before the batch — and the turn — ended) into the persisted history. The real guarantee against losing typed text is the client-side hold-until-ack invariant above; this only protects against the client's in-memory state being lost (e.g. a page refresh) before that invariant could fire.

- **Vision-capability cache** (`src/services/visionCache.ts`, `src/services/llmContextLimit.ts`):
  - Per-`(baseUrl, provider, modelName)` cache of vision (image-input) support, mirroring `capResolver.ts`: NUL-separated key, 5-minute TTL, `Map`-backed, and `invalidateVisionCache(...)` for model/baseUrl/provider changes.
  - **Resolution precedence**: OpenAI-compatible assumes `'supported'` when no runtime discovery exists; Ollama assumes `'unsupported'` only as a weak fallback. A successful Ollama `/api/show` capabilities probe refreshes a weak default or older probe, while a runtime-discovered rejection from a matching 400 remains authoritative for the TTL. Probe failures preserve a valid cache entry and otherwise fall back to the provider default.
  - **Reactive discovery**: `parseVisionUnsupportedFromError` in `src/services/llmContextLimit.ts` matches a small set of well-known 400-message patterns ("image input is not supported", "does not support image", "image_url is not supported", etc.). When the chat route's 400 catch block matches, it calls `recordDiscoveredNonVision(baseUrl, model, provider)` and emits an SSE `status` event with `phase: 'vision_unsupported'` so the client warning UI updates. Conservative on purpose — false positives would silently strip images from a model that actually supports them.
  - **Surface for callers**: `resolveVisionSupport(baseUrl, model, provider, probe?)` returns `{state, source}`. The chat route and `/api/models` use the async `getLlmModelVisionSupportAsync` facade; Ollama model-info capabilities are passed when available so model listing cannot poison the cache with the default. The legacy sync `getLlmModelVisionSupport(info)` remains defensive for metadata-only callers.
  - **Client warning UI**: `ChatInput.tsx` renders an inline amber `⚠` warning when the user attaches an image to a known non-vision model, and a softer `ℹ` "unconfirmed" hint for the `unknown` + openai-compatible case (the optimistic default has not yet been resolved for that model). The attach control stays enabled — the warning is informational, not a block.
  - **Invalidation**: `src/app/api/config/route.ts` calls `invalidateVisionCache(...)` for both the old and new `(baseUrl, model)` pair on model/baseUrl change — same conditions as `invalidateCapCache`.

- **Sampling-parameter cache** (`src/services/samplingParamsCache.ts`, `src/services/llmContextLimit.ts`):
  - Per-`(baseUrl, provider, modelName, paramName)` cache of standard sampling-parameter support (`temperature`, `top_p`, `frequency_penalty`, `presence_penalty`, `seed`, `stop`, `logit_bias`). Mirrors the vision-cache shape: NUL-separated key, 5-minute TTL, `Map`-backed, `invalidateSamplingParamCache(...)` for model/baseUrl changes.
  - **Resolution precedence**: a fresh `discovered` (reactive 400) entry wins over later probes until its TTL expires. Successful `supported_parameters` probes refresh a weak default or older probe. Provider default is `'supported'` for both openai-compatible and Ollama — Ollama's API accepts every sampling knob even when a specific model ignores it, and a wrong strip is worse than a redundant field.
  - **Proactive discovery**: `fetchSamplingParamSupport` on the openai-compatible adapter hits `GET /v1/models` and reads the model entry's `supported_parameters` list (OpenRouter exposes this; other providers ignore the field). The chat route fires the probe once per turn via `getLlmModelSamplingParamSupportAsync` and feeds the result into `params.samplingParamSupport`, which the adapter consults synchronously at request build time. This proactive path is main-chat-turn only — it needs a network round trip, so it isn't worth doing on every sub-agent/judge/compaction call.
  - **Reactive discovery is adapter-level, not route-level.** `parseUnsupportedParamFromError` in `src/services/llmContextLimit.ts` matches a small set of well-known 400-message patterns ("temperature is not supported", "unsupported parameter: temperature", "does not accept temperature", "value not supported for parameter `temperature`", etc.). `openaiCompatibleAdapter.ts`'s own catch blocks (`sendOpenAICompatibleChat` and `sendOpenAICompatibleChatStream`) parse every failed request through `recordUnsupportedParamIfDiscovered`, which calls `recordDiscoveredUnsupportedParam` directly — so ANY caller's 400 teaches the cache, not just the main chat route's. The chat route's own copy of this same parse+record block still runs too (recording the same verdict twice is harmless — it just refreshes the TTL) because it's also what emits the SSE `status` event (`phase: 'sampling_param_unsupported'`, `param`) that drives the client UI. Conservative on purpose — false positives would silently strip a sampling knob the model actually accepts.
  - **Every call site benefits automatically, with no wiring.** `resolveEffectiveSamplingParamSupport` in `openaiCompatibleAdapter.ts` prefers a caller-supplied `params.samplingParamSupport` (only the main chat route resolves this explicitly, via the proactive probe) and otherwise falls back to a synchronous cache peek (`peekSamplingParamSupportMap`, no network, no probe) before building the payload. This is what makes the cache apply uniformly regardless of who is calling `sendLlmChat`/`sendLlmChatStream` — sub-agents (`src/tools/impl/subAgentTool.ts`), the prompt-loop judge/critic (`src/services/promptLoop.ts`), compaction, and title generation never resolve or pass `samplingParamSupport` themselves, and don't need to: once ANY call has taught the cache that a model rejects e.g. `temperature`, every subsequent call from every caller silently omits it, without the caller knowing the cache exists.
  - **Adapter integration**: `src/services/adapters/openaiCompatibleAdapter.ts` walks the `SUPPORTED_SAMPLING_PARAMS` registry in `applySupportedSamplingParams`, omits any field marked `'unsupported'` by the effective support map, and uses a `(payload as Record<string, unknown>)[param] = value` cast to project onto the typed outbound payload. Fields absent from the registry or unsupported keep their existing behavior.
  - **Invalidation**: `src/app/api/config/route.ts` calls `invalidateSamplingParamCache(...)` for both the old and new `(baseUrl, model, provider)` triple on model/baseUrl change — same conditions as `invalidateVisionCache`.
