This file lists claims that are **not yet verified** and actions that are **still pending**. It is kept in the repository so that anyone (or any agent, on any machine) can pick an item up without needing the conversation that raised it.

## For AI agents: read and update this file

- **Read it first** before working on: the context window (`numCtx`), the OpenAI-compatible or Ollama adapters, retry or mid-turn model switching, compaction budgets, or the title route.
- **When your work verifies or contradicts an entry**, update it. Move a verified item to _Confirmed_ with the date and the evidence. If an entry is contradicted, say so, and correct any code or docs that relied on it.
- **When you write a "not verified" or "inferred" claim** in a commit message, a doc, or a reply, add an entry here with a way to confirm it.
- **Keep entries self-contained.** Someone with no conversation context, on another machine, should be able to run the check from the entry alone.
- **Never record secrets** (API keys, tokens, account details) here. Say where the key is kept (for example, `config.json`) and leave it there.
- **Expensive checks** (large prompts, paid calls) need the owner's go-ahead first. The entry says so.

### C-001 — llama.cpp: does `/v1/responses` pass `max_output_tokens` through?

- **Status:** Unconfirmed.
- **Claim:** Not confirmed: llama.cpp converts Responses requests to Chat Completions, and its docs do not say whether `max_output_tokens` survives that conversion. If it does not, the output caps Locopilot sets (summaries, digests, title) are silently ignored on a llama.cpp provider. Your local llama.cpp server may not pass the cap through.
- **Why it matters:** the adapter only calls `/v1/responses` (`src/services/adapters/openaiCompatibleAdapter.ts`, the `requestPath` default), so every llama.cpp provider depends on this.
- **How to confirm:** start `llama-server` with a small model, then run (replace the model name and port):
  ```bash
  curl -s http://127.0.0.1:8080/v1/responses -H "Content-Type: application/json" -d '{"model":"<model>","input":"Count from 1 to 300, one number per line.","max_output_tokens":16}'
  ```
  The cap works if the reply has `"status":"incomplete"` with `incomplete_details.reason` set to `max_output_tokens`, and `usage.output_tokens` is 16 or less. If it writes all 300 numbers, the cap is ignored. Run it again without the cap for comparison.
- **Needs:** a machine with llama.cpp built (`llama-server`) and a model. The owner's config points a provider at `http://localhost:60300`, which is a llama.cpp router on the owner's home machine.
- **Source:** web check of the llama.cpp server README (master branch), 2026-11-11. The README describes the conversion but not the field.

### C-003 — Does a local runner honour `options.num_ctx`, and how much memory does it reserve?

- **Status:** Partly confirmed. Two local models tested on this machine (2026-11-11, CPU only). The large-window question for a full-attention model is still open.
- **Honours `num_ctx`:** with `qwen3:0.6b`, a roughly 2,800-token prompt was cut to 130 tokens at `num_ctx` 256. So the runner truncates the input to the window.
- **Clamps above the model's own maximum:** with `qwen3:0.6b` (context 40,960), `num_ctx` 42,000 and 40,960 both reported `context_length` 40,960 and the same size, 5,500,211,034 bytes.
- **Reserves the cache up front:** with `bonsai-2:2b` (`qwen35`, `context_length` 262,144, a hybrid model), `/api/ps` size rose with `num_ctx`:
  - 8,192: 1,025,968,699 bytes
  - 32,768: 1,378,290,235 bytes
  - 65,536: 2,099,752,466 bytes
  - The server log's CPU KV buffer was 96, 384 and 768 MiB, which is exactly 12,288 bytes per token. The reserve happens at model load, not on demand.
- **The simple per-token formula overstates the cache for hybrid models.** Layers × KV heads × (key + value length) × 2 gives 49,152 bytes per token for this model. The log shows 12,288, because only 6 of its 24 layers keep a full-attention cache. Use the log figure, or count only the full-attention layers.
- **Not yet tested:** `num_ctx` 131,072 and 262,144 for this model, which the 6 GB budget blocked. The projected cache is 1.6 GB and 3.2 GB at those sizes. Whether the compute buffer also grows is unknown. And the clamp above `context_length` is untested on this model.
- **Why it matters:** the cache size depends on the model's architecture, not only on `num_ctx`. A full-attention model of similar size could need about 49 KB per token, which is about 12.9 GB at 262,144 tokens. So a model-specific check is needed before the server sends a large window to local runners.
- **How to reproduce:** `POST /api/chat` with `options.num_ctx`, read `GET /api/ps`, then unload with `POST /api/generate` and `keep_alive: 0`. Read the server log for the KV buffer size.
- **Needs:** the owner's machine, ideally with a GPU, to run the larger sizes. The compute buffer at those sizes is unknown.
- **Installed for testing on this machine:** `qwen3:0.6b`, `bonsai-2:2b` (911 MB) and `tev1:0.8b` (833 MB). `tev1:0.8b` refused chat requests ("does not support chat") and can be removed on request.

### C-014 — For llama.cpp, which maximum is enforced: the trained context or the served window?

- **Status:** Mostly answered (2026-11-11). Three models tested live. One model (Muse-Glimmer) still needs a live check; the source predicts a result for it.
- **Result (live):** the enforced limit is the **served** window, not the trained context that `/v1/models` lists as `context_length`.
  - `Nemotron-3.5-Lightning-30B-A3B-UD-Q4_K_XL`: `context_length` 1,048,576, `--ctx-size 393216`, served `n_ctx` 393,216. A 429,927-token prompt was refused in about 1 second with `request (429927 tokens) exceeds the available context size (393216 tokens)`. The loaded `meta.n_ctx_train` also reads 393,216, which fits a YaRN rewrite (see the source below).
  - `Ornith-1.5-35B-A3B-Heretic-MTP-APEX` (no `--ctx-size`): `context_length` 262,144, served `n_ctx` 222,976 (sized by llama.cpp at load to fit memory). A 239,960-token prompt was refused with `exceeds the available context size (222976 tokens)`.
  - `Ornith-1.5-35B-A3B-Heretic-MTP-APEX-I-Quality` (`--ctx-size 262144`): served 262,144, equal to its `context_length`. This case does not discriminate.
- **Result (live):** a single 109,987-token prompt was accepted on the Nemotron model, which has 4 slots. A single request can use the whole served window.
- **Result (live):** the refusal's JSON body carries `"n_ctx"` with the enforced value (for example `"n_ctx":393216`). This is the most reliable value to read at request time.
- **Source (llama.cpp tag `b12124`, read by a research agent; the key check spot-verified by hand on 2026-11-11):**
  - The 400 is raised in `tools/server/server-context.cpp` around line 4081, by `slot.task->n_tokens() >= slot.n_ctx`, and the value is the per-slot context.
  - The per-slot value comes from `n_ctx_slot()` (line 5066): the smallest of the per-sequence context, `--kv-unified-per-slot` if set, and the trained context after any YaRN rewrite.
  - `context_length` in `/v1/models` is set from the GGUF key `<arch>.context_length` (`tools/server/server-models.cpp` around lines 2133–2225, and `common/common.cpp` around 1247). It ignores `--ctx-size`, RoPE and YaRN. That is why it differs from the served value.
  - With `--rope-scale` and YaRN, `src/llama-context.cpp` around 4383 sets `n_ctx_train` to `n_ctx_orig_yarn / rope_freq_scale`. For Nemotron, 262,144 / (1/1.5) = 393,216, which matches both its `--ctx-size` and its loaded `n_ctx_train`.
  - A `--ctx-size` above the trained context is accepted, but each slot is capped at the trained value (warning at `server-context.cpp` around 1464).
- **Predicted, not yet tested:** `Muse-Glimmer-30B-Q4_K_M` (`context_length` 131,072, `--ctx-size 262144`, no YaRN) should be enforced at **131,072**, because the trained value caps each slot. A request above 131,072 should be refused with `(131072 tokens)`.
  - The owner recalls that this model natively supports a 128K window, which is 131,072 tokens. That is consistent with the prediction, but it is the owner's recollection and has not been checked against the model card.
- **Still open:** the Muse load failed twice (HTTP 500, "failed to load") on 2026-11-11, and the router's logs are not reachable from here. To test the prediction, load it on the owner's router and send a prompt of about 140,000 tokens with `max_tokens: 1`.
- **Built in Phase 2 (2026-11-11):** `getLlamaCppServedWindow` in `src/services/llmContextLimit.ts`. A llama.cpp model is known only when its `/v1/models` entry has `meta.n_ctx` and its `status.value` is `loaded` (or there is no `status`, as on a plain llama-server). `context_length` and `n_ctx_train` are never used, and an unloaded model is unknown. Checked with fixtures, and through the real adapter mapping against a local test server (`tests/numctx-resolver.test.mjs`). **Not checked live against the owner's router**: it was not reachable from this machine on 2026-11-11 (HTTP 000 on `localhost:60300`). The resolver reads the served window from the model list, not from `GET /props?model=` or from a refusal's `n_ctx`; the refusal body is still learned from through its message.
- **Consequence for Phase 2 (as planned):**
  - `context_length` from `/v1/models` is not the maximum to clamp to for llama.cpp.
  - For a loaded model, read the served value from `GET /props?model=<name>` (`default_generation_settings.n_ctx`), or from the refusal's `n_ctx`.
  - For an unloaded model, the enforced value depends on `--ctx-size`, the trained context, and any YaRN rewrite. It is not reliably known before the model loads, so the resolver should treat it as unknown until then.
- **How to reproduce:** `POST /tokenize` with `{"model": "<name>", "content": "..."}` counts tokens exactly. Then send `POST /v1/chat/completions` with `max_tokens: 1` and a prompt just above the expected size. The error body names the enforced value.
- **Could not verify (per the research):** whether `GET /props?model=` loads an unloaded model, the owner's GGUF `rope_freq_scale_train`, and the `--parallel` behaviour on the owner's build. The owner's router log line "custom YaRN scaling detected" would confirm the YaRN rewrite.

### C-015 — The reduction's overhead is measured with a made-up window (`numCtx: 200000`)

- **Claim:** `countReductionRequestOverhead` (`src/services/compact/reduce.ts`, around line 420) counts what a combine request carries besides the partial summaries. - **How to confirm:** at `numCtx` 1,048,576, build the retry prompt with `computeSummaryBudget(1048576, 1, <safe input budget>)` and the real user prefix, count it with `countMessagesTokens(..., 'summarise')`, and compare with the number `countReductionRequestOverhead` returns for the same model and focus.

### C-017 — Counting a long run of one repeated character is very slow

- **Status:** Observed (2026-11-12); real-world occurrence not checked.
- **Observed** (this machine, `countRawMessagesTokens`, `cl100k_base`, a message that is `"x"` repeated): 10,000 characters took 87 ms, 20,000 took 210 ms, 40,000 took 845 ms, 80,000 took 3.4 s and 160,000 took 13.9 s. The time roughly quadruples each time the length doubles. Ordinary varied text of 4,000,000 characters took 563 ms.
- **Why it matters:** every history count (the compaction trigger, `countMessagesTokens` before and after a compaction, the preserved-window budget) runs over whole tool outputs. A tool output that is one long run (a rule of `=` signs, padding, a minified blob) could stall a turn for seconds, and a larger one for minutes. The distiller's 112,000-character input cap does not help, because the whole history is counted before it is cut.
- **Not verified:** whether real tool outputs reach such lengths; other repeated patterns (a repeated word, base64); the production Node and WASM build.
- **How to confirm:** time `countMessagesTokens([{ role: 'user', content: 'x'.repeat(n) }], model)` for growing `n`, then try a long base64 string and a minified file of the same size. If real outputs are affected, the fix belongs in `src/services/tokenizer.ts` (for example, estimate by length above a size or run threshold), and it changes every count, so it needs its own change.

### C-025 — A global default compaction model cannot name its provider

- **Status:** FIXED (2026-11-16, branch `feature/global-compaction-provider`). The gap below was real and was closed; the evidence is kept because it explains the design. The residual risk is recorded as C-026.
- **Claim (the gap, as it was):** the GLOBAL default compaction model can name a model but not a provider, so a conversation that pins no compaction provider of its own has its compaction call sent to the MAIN provider. If the global compaction model is served by a different provider than the main model, every compaction call goes to the wrong provider — including every web-page compaction, which then truncates each page instead of summarising it.
- **Evidence (2026-11-16, the owner's production copy, BEFORE the fix):**
  - The global `Config` has `compactionModel?: string` (`src/types/chatConfig.ts:164`) and NO `compactionProviderId`.
  - The client's defaults body (`defaultsBody()`, `src/app/lib/sessionSelectionClient.ts`) sends `compactionModel` but never a compaction provider, so the global default can never carry one.
  - `resolveCompactionRuntime` (`src/app/api/chat/route.ts:1178-1209`) resolves the compaction provider by EXPLICIT ID only; with no id it falls back to `llmRequestContext`, the main provider. The compact and title routes carry a comment saying the same thing — that falling back to model-name resolution is unsafe, because `resolveProvider` matches only a provider's default `model` field and otherwise returns `providers[0]` — **but their CODE does not do what the comment says**: both pass the compaction model into the resolver (`src/app/api/compact/route.ts:224-231`, `src/app/api/title/route.ts:147-154`), so a dangling compaction id there resolves BY MODEL to a different provider and uses that provider's apiKey. The chat route's compaction path and the compact/title compaction paths therefore behave differently on a dangling id: chat falls back to the main provider, compact/title cross-wire to a third provider.
  - 0 of the 475 sessions in the production database pin `compaction_provider_id`.
- **How it bit (2026-11-15/16, production):** the global default compaction model was `beam`, an OLLAMA CLOUD model. A conversation on the NVIDIA provider (`nvidia/nemotron-3-ultra-550b-a55b`, which the provider matched by model name because the session pinned no provider) inherited `beam` and sent it to `https://integrate.api.nvidia.com/v1/responses`, which answers HTTP 404 "404 page not found". 221 such failures in 14 minutes under one request id; every web page was then truncated to `perPageCharLimit` instead of being summarised.
- **The per-conversation remedy already works.** Picking the compaction model WITH its provider in the ModelSelector writes `compaction_provider_id` on the session row (`handleSelectCompaction(nextCompactionModel, providerId)`, `src/components/ModelSelector/ModelSelector.tsx`). The gap is only in the GLOBAL default.
- **How to confirm a fix once it exists:** (a) with a global `compactionProviderId`, set the global compaction model to a model the active provider does not serve and check that the compaction call reaches the NAMED provider; (b) without one, check that the server answers with a clear "the compaction model needs a provider" refusal instead of silently calling the main provider. The refusal is the safer of the two IF the server has only `config.json` to work from: guessing by model name cannot work from the file alone, because a provider's full model list is not in `config.json` (the owner's `ollama-cloud` provider has no `model` field at all). It CAN work if the server builds the map from the LIVE model lists, which `GET /api/models` already does for every provider (`src/app/api/models/route.ts`); the client uses exactly that list to re-point a dangling active provider id (`src/app/hooks/useDataLoaders.ts:345-367`). A cached server-side model → provider index is therefore the missing ingredient, and it would also let the server VALIDATE a pinned (model, provider) pair instead of trusting it.
- **What was implemented (2026-11-16, `feature/global-compaction-provider`):**
  - The global `Config` gained `compactionProviderId?: string | null` (`src/types/chatConfig.ts`): the provider that serves the global compaction model. `null`/absent = "no global compaction provider", so compaction runs on the main chat provider. It is CLEARABLE (`PUT /api/config` accepts a string or `null`; `''` normalises to `null`) and is resolved BY ID ONLY, never by model name.
  - ONE rule, in `src/services/compactionRule.ts` (`resolveCompactionRule`, dependency-free so the browser and the server share it), and ONE server composer around it (`src/services/compactionSelection.ts`, `resolveCompactionSelection`). The four divergent sites — the chat route's preflight, the chat route's runtime, the compact route and the title route — now all go through the composer. The preflight/runtime disagreement and the compact/title cross-wiring recorded above are gone: every site resolves the compaction provider BY ID ONLY and applies the same order (session pin → global pair → the conversation's own main model on the main provider).
  - The invariant that produced the 404s is now explicit and tested: a model is never handed to a provider that was pinned for a DIFFERENT model. A conversation that pinned a compaction model of its own but no provider runs on the global provider ONLY when the global provider serves that very same model; otherwise on the main provider.
  - A pinned compaction provider that names no configured provider is now a REFUSAL (HTTP 409 naming the id) instead of a silent fallback — for a session pin and for the global pin alike. The blast radius (a broken compaction config blocks the chat turn) is deliberate. `/dump` is exempt - and since 2026-11-17 it never refuses for the configuration at all (it makes no model call; it reports a removed provider, a missing window or an unreadable `config.json` in the file): dumping is the tool you reach for when something is broken. The mid-turn switch path does NOT refuse — it logs a `compaction_provider_unresolved` diagnostic and falls back to the main context, because a running turn must not die.
  - A compaction provider needs a window of its own: `compactionProblemFor` (`src/services/contextWindow/configProblem.ts`) also checks the resolved compaction provider's own `numCtx`.
  - The client OMITS and the server resolves: the chat body carries `compactionModel` / `compactionProviderId` only when the conversation PINS them; `''` survives to the server as "same as the main model". The global pair is written together (`{ compactionModel: name, compactionProviderId: providerId ?? null }`), and "Use the default" writes NEITHER.
  - Covered by `tests/compaction-rule.test.mjs` (23 tests: the rule's table, the anti-404 invariant, the refusal, and the input hygiene).
  - **NOT verified live.** No browser and no provider was exercised against the new field. See C-026.
- **Criterion (b) met for the TURN-START path (2026-11-17, branch `feature/provider-pair-integrity`).** The criterion was: *"(b) without one [a global compaction provider], check that the server answers with a clear 'the compaction model needs a provider' refusal instead of silently calling the main provider."*
  - It is met in the form this entry itself sanctions - the LIVE model lists - and deliberately NOT as an unconditional refusal. An unconditional refusal would block every conversation that inherits a global compaction model whose main provider DOES serve it, and a false refusal is worse than the bug it prevents.
  - The gap was real and was still open on 2026-11-17: with a warm index, `compactionProblemFor(config, {mainModel: 'llama3', mainProvider: <NVIDIA>, compaction: {kind: 'inherit-default'}})` returned `null` for a config whose global compaction model was `beam` and whose main provider did not serve it. The same `beam`-to-NVIDIA 404 this entry describes was still reachable.
  - What is true now, at turn start: a compaction model with no provider of its own runs on the provider the CHAT runs on, and THAT provider is asked whether it serves it. With a warm index and the answer "not served", the turn is refused with HTTP 409 and a message that names the provider that does not serve the model AND the one that does. With a cold index - never fetched, fetch failed, empty list - the answer is "unknown" and the turn is ALLOWED, deliberately, because a dead or slow provider must not block a turn.
  - The check is made against the RESOLVED main provider (the request's own provider id), never against `providers[0]`: the owner's `ollama-cloud` provider has no `model` field, so a resolution that dropped the id would check NVIDIA and refuse a turn that works.
  - CLOSED (2026-11-17, `feature/provider-pair-integrity`): the MID-TURN SWITCH path is checked as a pair too. `planModelSwitch` forms the pair the switch would form and puts it through the same checks a new turn is put through, and an incoherent switch is refused WHOLE. See C-030.

### C-026 — A pinned (compaction model, compaction provider) pair is never checked against a live model list

- **Status:** FIXED (2026-11-16, branch `feature/provider-pair-integrity`). The gap below was real and was closed; the evidence is kept because it explains the design.
- **Claim (the gap, as it was):** the server resolves a compaction provider BY ID and trusts the pair. It never asks the provider whether it actually serves the compaction model, so a pair that names a real provider but a model that provider does not serve still produces a 404 (the same shape as the production failure, reached a different way).
- **Why it mattered:** C-025 closed the case where the id named NO provider. This was the case where the id names a provider that does not serve the model. The client knows the answer — `GET /api/models` returns every provider's live model list with each model's real `providerId` — but the server did not consult it, and `config.json` cannot answer it (a provider's full model list is not in the file; the owner's `ollama-cloud` provider has no `model` field at all).
- **How it was confirmed (2026-11-16, in code):** `resolveCompactionSelection` (`src/services/compactionSelection.ts`) refuses an id that names no configured provider and then resolves the provider BY ID ONLY — but it never asks the provider whether it serves the model. `configProblemFor` (`src/services/contextWindow/configProblem.ts`) checked the provider's WINDOW and nothing else, so a pair naming a real provider that does not serve the model passed the gate and 404ed at the provider.
- **What was implemented (2026-11-16, `feature/provider-pair-integrity`):**
  - A cached server-side model → provider index (`src/services/modelIndex.ts`), built from the live lists `GET /api/models` already fetches. The models route records each provider's list (`recordProviderModels`) and each failure (`recordProviderListFailure`).
  - The index is read SYNCHRONOUSLY (a cache peek, no network on the chat path). A successful list is trusted for 5 minutes; a failed one for 60 seconds; the key is (provider id, base URL), so a provider whose ADDRESS changed does not answer with the old list.
  - The answer is THREE-valued: `served`, `not-served`, `unknown`. Unknown NEVER refuses — a cold cache, a failed fetch and an empty list all answer unknown, because a dead or slow provider must not block a turn.
  - The pair check lives in `configProblemFor`, so it covers the MAIN pair and the COMPACTION pair alike (the compaction provider's window check goes through the same function). A pair whose provider does not serve the model is refused with a message that names the offending provider AND the provider that DOES serve the model, so the fix is one pick in Settings.
  - The Ollama tag tolerance follows the adapter's existing rule (`ollamaAdapter.ts`): `llama3` names `llama3:latest` and `llama3:8b`.
  - A background refresh keeps the index warm: the caller passes the config it already has, the sweep runs at most once a minute, and each provider is fetched at most once a minute and one at a time. The chat path never waits for it.
  - Covered by `tests/model-index.test.mjs` (12 tests).
  - **NOT verified live.** No browser and no provider were exercised against the new refusal.
- **Still worth knowing:** the check can only refuse when the index holds a FRESH list for that provider. A provider whose list was never fetched (or whose fetch failed) answers unknown, so its pair is trusted — the same as before this change.

- **Evidence (2026-11-16, verified in code):**

### C-028 — The compaction model and its provider were two independent fields, so a model could be pinned without the provider that serves it

- **Status:** FIXED (2026-11-16, branch `feature/provider-pair-integrity`). The gap below was real and was closed; the evidence is kept because it explains the design. One of the defences this entry lists - the WRITE path normalising the pair - was not actually true until 2026-11-17; see the note under "What was implemented" below.
- **Claim (the gap, as it was):** the session's compaction selection was TWO nullable columns (`sessions.compaction_model`, `sessions.compaction_provider_id`), which admitted FOUR states: `(NULL,NULL)` inherit-default, `('',NULL)` same-as-main, `('x','p')` explicit, and `('x',NULL)` — **a compaction model with no provider**. The fourth is the bug class: the model was handed to whichever provider the rule fell back to, which is not necessarily the one that serves it, and the call 404ed with nothing to explain why. The rule even had a branch for it ("a conversation that pinned a model of its own but no provider"), which papered over the incoherence instead of removing it.
- **Why it mattered:** the pair is what makes a compaction call go to the RIGHT endpoint. The two fields could drift apart, and once apart nothing could tell that they had: the row, the wire and the SSE frame all carried two independent values.
- **How it was confirmed (2026-11-16, in code):** `sessions.compaction_model` and `sessions.compaction_provider_id` were independent nullable columns (`src/services/history.ts`); the store held `compactionModel` and `compactionProviderId` as two fields (`src/app/lib/chatStore.ts`); the chat body carried them as two optional fields (`src/app/hooks/useChatStream.ts:677-678`); and the rule resolved them independently (`resolveCompactionRule`, before this change).
- **What was implemented (2026-11-16, `feature/provider-pair-integrity`):**
  - The pair is now ONE value with THREE states — `CompactionSelection` in `src/services/sessionSelection.ts`:
    ```ts
    | { kind: 'inherit-default' }
    | { kind: 'same-as-main' }
    | { kind: 'explicit'; model: string; providerId: string }
    ```
    The fourth state cannot be represented, so it cannot be resolved, stored or sent.
  - `resolveCompactionRule` reads the union, and its "a conversation pinned a model but no provider" branch is DEAD. The rule's three states map onto the existing columns without a schema change: `NULL/NULL` → inherit-default, `''/NULL` → same-as-main, `'x'/'p'` → explicit.
  - `compactionSelectionFromPair` is the STRICT converter: a named model without its provider is REFUSED with a message that says what to send instead, and a provider without a model is refused too. `compactionSelectionFromLoosePair` is the lenient one, for the places that must not fail (reading a row, showing what a conversation compacts with); it repairs towards "inherit the global default", which always names a model AND a provider that belong together.
  - Defence in depth: the write path normalises (`selectionToColumns` → `coherentCompactionPair`; until 2026-11-17 it called the PURE PROJECTION `compactionSelectionToPair`, which does NOT normalise, so the claim in this entry was false until then), the read path normalises (`selectionFromColumns`, and `listSessions` / `searchSessions` for the rows the browser reads), the `model-changed` SSE frame announces the NORMALISED selection, `PATCH /api/sessions/[id]` refuses a patch whose selection does not parse AND refuses a legacy flat patch that names only one half of the pair, `POST /api/sessions` refuses an incoherent selection at creation, and a bootstrap step rewrites the illegal rows in place.
  - The database schema is unchanged (the columns already encode the three states) and the GLOBAL config keeps its two-field shape (`config.json` is hand-edited).
  - Covered by `tests/compaction-rule.test.mjs` (32 tests), `tests/session-model-selection.test.mjs` (43 tests) and `tests/session-compaction-pair.test.mjs` (9 tests, the route driven in-process).
  - THE WRITE PATH NOW NORMALISES (2026-11-17, `feature/provider-pair-integrity`). The bullet above was FALSE until then: `selectionToColumns` called `compactionSelectionToPair`, which is a pure projection and repairs nothing, so a caller that built a half-pair by hand could still write one to the row - and the `model-changed` frame announced the raw selection rather than the normalised one. Both are fixed: the projection now goes through `coherentCompactionPair` (the SAME repair the read path uses), and the frame carries the pair that was actually written. The test that claimed to cover this read the NORMALISED projection rather than the raw row, so it passed while the row held the half-pair; it now reads the raw row.
  - **NOT verified live.** No browser and no provider were exercised against the new refusals.
- **Phase 2.4 (2026-11-16, same branch) closed the "still open" gap below.** The STORE and the WIRE now carry the union, so the compiler catches a half-pair instead of the boundary checks:
  - `ChatState.compaction` is a `CompactionSelection`; `ChatState.compactionModel` / `compactionProviderId` are gone. `SessionSelection.compaction` and `SessionSelectionPatch.compaction` are the union too.
  - Every request body carries `compaction` — chat, `/compact`, `/title`, `POST /api/sessions`, `PATCH /api/sessions/[id]`, `POST /api/chat/switch-model` — and so do the `session_created` and `model-changed` SSE frames.
  - The LEGACY flat pair is still READ, in exactly one place (`compactionSelectionFromPayload`), so a tab that was open before the change keeps working. `compactionPairProblem` and `compactionPairPatchProblem` are gone: a half-pair has no spelling, so a check for one was vacuous. What remains is `legacyCompactionPairPatchProblem`, which guards the OLD wire shape only.
  - The conversation's own ROW keeps the two columns (the schema is unchanged). The pair reaches the row only through `compactionSelectionToPair` and leaves it only through `compactionSelectionFromLoosePair`.
  - `src/services/modelManager.ts` (`resolveCompactionModel`) was removed: the rule resolves the loose pair now, and nothing referenced it.
  - **NOT verified live.** The client paths were exercised by the test suite only.

### C-029 — The GLOBAL compaction pair is still two independent fields, so a global model can name a provider that does not serve it

- **Status:** OPEN. Deliberately left as it is; recorded here so the gap is not mistaken for an oversight.
- **Claim:** `config.compactionModel` and `config.compactionProviderId` are two independent fields in `config.json` and in `Config` (`src/types/chatConfig.ts`). The rule reads them as a pair (`resolveCompactionRule`'s `globalCompactionModel` / `globalCompactionProviderId`), and the global model runs on the global provider when one is set — so the same "a model is handed to a provider that was pinned for a DIFFERENT model" shape is still expressible at the GLOBAL level: a `config.json` with `"compactionModel": "beam"` (an Ollama Cloud model) and `"compactionProviderId": "nvidia-openai"` sends a cloud model to NVIDIA.
- **Why it is NOT fixed here (Phase 2.4):**
  1. The global pair is `config.json`'s shape and the file is hand-edited. The plan explicitly keeps it (`docs/PROVIDER_PAIR_PLAN.md`, "What is deliberately NOT changed").
  2. "A global model with no provider of its own" is a LEGITIMATE meaning — the model, on the provider the chat runs on. The conversation's own pair had no such state, which is why the union was right there and not here.
  3. The client always writes the global pair TOGETHER (`defaultsBody` in `src/app/lib/sessionSelectionClient.ts`; the ModelSelector and the Settings modal both send `{ compactionModel, compactionProviderId }`), so the compiler guarantee would buy nothing at the global level.
  4. The rule resolves the global provider BY ID ONLY and never by model name, so a dangling global id is a 409 (`compactionProblemFor`) rather than a silent cross-wire. What is NOT checked is whether the named provider serves the named model — that is C-026, and it is now answerable: the cached server-side model index (`src/services/modelIndex.ts`) can validate the global pair exactly as it validates a conversation's pair.
- **How to confirm it (once someone wants to close it):** set `"compactionModel"` to a model of provider A and `"compactionProviderId"` to provider B's id in `config.json`, then start a conversation that INHERITS the global compaction selection (the default) and watch which endpoint the compaction call reaches. `logs/locopilot-debug.log` records the compaction provider, model and baseUrl at the `compaction_start` phase.
- **NOT verified live.** The reasoning above is from the code, not from a run.
- **The SERVING question is now answered in BOTH shapes (2026-11-17, `feature/provider-pair-integrity`).** This entry is about the SHAPE - two independent fields in `config.json` - and the shape is still deliberate and unchanged. What changed is that neither shape is TRUSTED any more:
  1. a global pair that names a provider is validated against the live model list (`configProblemFor`), so `"compactionModel": "beam"` with `"compactionProviderId": "nvidia-openai"` is refused with a 409 naming the provider that does serve `beam`;
  2. a global model with NO provider of its own runs on the provider the chat runs on, and THAT provider is validated against the live model list too (C-025's criterion (b), and C-030).
  So the residual is the `config.json` SHAPE only. It is no longer a silent wrong endpoint: the mid-turn switch path was closed on 2026-11-17 as well (C-030).

### C-030 - An inherited global compaction model was sent to the main provider, unchecked

- **Status:** FIXED (2026-11-17, branch `feature/provider-pair-integrity`), for the TURN-START path and for the MID-TURN SWITCH path. The switch half landed the same day; see "What was implemented" below.
- **Claim (the gap, as it was):** a conversation that INHERITS the global compaction selection, with a global `compactionModel` and NO global `compactionProviderId`, had its compaction model sent to the provider the CHAT runs on, with no check that the provider serves it. The branch's new model index was applied to the MAIN pair and to an EXPLICIT compaction pair, but NOT to this one - so the original production failure, `beam` to NVIDIA and HTTP 404, was still reachable.
- **How it was confirmed (2026-11-17, in code, and by probe):** `compactionProblemFor` (`src/services/contextWindow/configProblem.ts`) returned `null` as soon as the resolved compaction provider id was `null`, with the comment "The MAIN provider - the main check already covered its window". The main check had covered the MAIN MODEL's window, never whether the main provider serves the COMPACTION model. With a warm index (`NVIDIA` serving `llama3`, `Ollama Cloud` serving `beam`): `configProblemFor(config, 'nvidia', 'beam')` returned "The provider \"NVIDIA\" does not serve the model \"beam\"..." while `compactionProblemFor(config, {mainModel: 'llama3', mainProvider: <NVIDIA>, compaction: {kind: 'inherit-default'}})` returned `null`.
- **What was implemented (2026-11-17, `feature/provider-pair-integrity`):**
  - `compactionProblemFor` now takes the provider the CHAT runs on (`mainProvider`) and, when the compaction inherits it and the compaction model is NOT the main model, asks the model index whether that provider serves the model.
  - The answer is three-valued, and `unknown` never refuses: a cold cache, a failed fetch and an empty list all let the turn proceed. The background refresh is kicked so the NEXT turn can ask the question instead of guessing.
  - The check is made against the RESOLVED main provider - the request's own provider id - never against `providers[0]`. The owner's `ollama-cloud` provider has no `model` field, so a resolution that dropped the id would check NVIDIA and refuse a turn that works.
  - A refusal names the provider that does not serve the model AND the one that does, and says what to change: set `compactionProviderId` in `config.json`, or pick a compaction model and provider that belong together.
  - `same-as-main` and a conversation with no global compaction model are NOT checked again: the main pair check already answered them. An EXPLICIT compaction pair is still checked against its OWN provider.
  - The chat route's runtime records a `compaction_model_not_served` diagnostic when the compaction inherits the main provider and that provider does not serve the compaction model. It fires at TURN START as well as after a mid-turn switch: the gate and the runtime read `config.json` separately, so they can already disagree. The turn is not refused - a running turn must not die - but the condition is visible in the log instead of being a bare 404.
  - Covered by `tests/model-index.test.mjs` (11 new tests) and `tests/provider-resolution.test.mjs` (3 new tests). One of the new tests in each file fails if this change is reverted; the rest are forward guards against an over-broad fix (a cold index, `same-as-main`, an explicit pair, and the case where the main provider DOES serve the compaction model).
  - THE MID-TURN SWITCH, THE SAME DAY. The switch was the last path that introduced a new pair without checking it. `planModelSwitch` (`src/services/contextWindow/configProblem.ts`) forms the pair the switch WOULD form and puts it through the same checks a new turn is put through; an incoherent switch is REFUSED WHOLE (the turn keeps the model and the provider it already runs on, and the compaction keeps the selection it already has), and the refusal is announced on a new SSE phase, `model_switch_refused`, carrying the reason. The client reports it instead of swallowing it: `requestMidTurnModelSwitch` returns `{accepted, message}` and the message reaches the error banner. "Use the default" is now carried by the switch as `compaction: {kind:'inherit-default'}` - the union can say it, the old flat pair could not - so the pick is no longer dropped and no empty request is sent. Covered by `tests/mid-turn-switch.test.mjs` (new) and `tests/sse-routing.test.mjs`.
- **Still open:** nothing on this entry. The decision the owner took is recorded here: an incoherent switch is refused WHOLE, and the refusal is reported rather than swallowed. The turn itself stays alive - it keeps the model and the provider it already runs on.
- **Still worth knowing (updated 2026-11-17):** the refusal depends on the model index holding a FRESH list for the main provider. A list up to 5 minutes old can wrongly answer "not served". The background refresh is now kicked on "not served" as well as "unknown" (bug hunt A12), so such a refusal heals within about a minute rather than at the end of the TTL; the ask that triggered it is still refused. Whether the index matches what Ollama Cloud and NVIDIA actually list is NOT verified live. This is the same exposure the MAIN-pair check already has (C-026); this change does not invent it, but it adds a second pair that can refuse a turn on a stale answer.
- **NOT verified live.** No browser and no live provider were exercised against the new refusal.

- **Provider IDs are stable WHILE the provider is configured (2026-11-16, verified in code).** A provider's id is made from its NAME at creation time (`uniqueProviderId`, `src/services/providerValidation.ts:109-125`): the name is lowercased, non-alphanumerics become `-`, and a numeric suffix is appended if the slug is taken. `POST /api/providers` is the only writer that generates one, it is add-only (no edit or delete route), and the client cannot supply an id through it ("an id, a window or anything else the caller sends is ignored"). The provider's address, kind and API key stay in `config.json`, so a conversation that stores only the id follows the provider when its address changes. **Three caveats:** (1) because the id is derived from the name, hand-renaming a provider in `config.json` changes its id and breaks every link to it; (2) the uniqueness check is only against the ids CURRENTLY in `config.json` (`existing.map(p => p.id)`), so an id IS reused after the provider is removed — there is no DELETE route, but `PUT /api/config` replaces the whole `providers` array, and re-adding a provider with the same name then regenerates the same id (the header comment "the id is made from the name and never reused" holds only among currently-configured providers); (3) `PUT /api/config` accepts ANY id a client writes and `validateConfig` runs `validateProvider` per entry with no cross-entry uniqueness check, so two providers can end up sharing an id and `resolveProvider`'s `providers.find(p => p.id === providerId)` then always picks the first.
- **What happens when a stored provider id no longer resolves (2026-11-16, verified in code; FIXED the same day).** `resolveProvider` (`src/services/providerResolver.ts`) returns `null` for an explicit id that matches no provider — it deliberately does NOT fall back to `providers[0]`, because that would cross-wire another endpoint's baseUrl and apiKey. It used to cross-wire by MODEL NAME as well: `providers.find(p => p.model === modelName)` ran before the `null` return, so a dangling id plus a model that equals some provider's default `model` silently returned that other provider, with its apiKey. Whether a dangling id "fell back" therefore depended entirely on whether the call site passed a model. The outcomes differed per route:

The model name is used only when the request carries no id at all.

  - The compact and title routes resolved their compaction provider by ID **and** model (`src/app/api/compact/route.ts:224-231`, `src/app/api/title/route.ts:147-154`) → a dangling compaction id cross-wired to a DIFFERENT provider, using that provider's apiKey. This was the opposite of the chat route, and it contradicted the comment directly above it. **Fixed 2026-11-16** (C-025): both routes now resolve BY ID ONLY through `resolveCompactionSelection`, and refuse a dangling id instead of cross-wiring.
